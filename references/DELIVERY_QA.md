# 交付與品管（台灣 Hermes 基線）

## 1. 與使用者確認（必做）

完成一輪可辨識交付後，**主動簡短確認**是否符合需求。  
不符 → 修正 → 再確認。

## 2. 檔案交付前：subagent **純視覺 QA**（必做）

### 正確理解

| 誤解 | 正確 |
|------|------|
| 檔案一定要叫 subagent 去**產出** | 產出可由主 agent 做 |
| 只跑機械 QA 就好 | 必須有人（subagent）**看圖** |
| 同一長對話自己喊過關 | 必須**獨立、乾淨上下文**的 subagent |

**規則一句話**：涉及檔案交付（PDF／簡報／圖／畫面型產物等）→ 交使用者前先派 **subagent 做純視覺 QA**。

### 檔位紅線（2026-08-10 定案）

視覺 QA 一律用**當前可用最高檔**：

- 模型檔位與思考強度都取最高；**禁止中階、禁止最便宜**
- **禁抽樣**：所有頁／所有圖**逐張看**（20 頁就 20 張，不能只看 3 張）
- **機械過關不算通過**：DOM 檢查、量測、lint 全過仍要有人看圖
- **禁自評過關**：不能同一長對話自己喊過；必須獨立乾淨上下文的檢查員

### 怎麼做

1. 主 agent（或既有流程）產出檔案  
2. **另開 subagent**，只給：檔案路徑、驗收重點、需求摘要（勿塞整段污染上下文）  
3. Subagent **純視覺**：轉頁圖／開圖逐頁看，回報問題清單  
4. 有問題 → 主線修正 → 必要時再派視覺 QA  
5. 通過 → 才正式交付 → 做第 1 節使用者確認  

### 看什麼（依類型）

- 字可讀、無疊字／裁切  
- 留白依相關性；避免上密下空、硬撐空白  
- 對齊、表格、元素是否溢出  
- 封面／滿版是否糊成一片或近純白（若適用）  

機械量測可先跑，**不能取代**純視覺。

### 故障處理（2026-08-25 實戰）

- 子代理**第一次 LLM 呼叫就斷**（通道問題）→ **重派，不能放棄**；連續失敗就換派法
- 重派期間主 agent **自己逐頁目視當雙保險**，兩邊結果都看
- 通道壞不能當作「跳過視覺 QA」的理由；紅線沒有例外

## 3. 建議流程

```text
產出檔案（主 agent 可）
  → subagent 純視覺 QA（必）
  → 修正（若需要）
  → 正式交付給使用者
  → 確認是否符合需求
```

## 4. 與 Telegram 富訊息

文字裡的狀態／對照：**表格優先**（`TELEGRAM_RICH.md`）。  
那是訊息排版；**檔案**交付前的純視覺 QA 不因此省略。

## 5. 工具回報 ≠ 事實（2026-08 事故教訓）

工具說「成功」只是**自報**，不是證據。對有外部副作用或落庫的動作，一律再驗證一次：

- **寄信／發布**：不信批次腳本回報成功；直接查落庫欄位（如 `sent_at`）或讀端實際狀態
- **寫入／部署**：檔案改了要確認讀端／線上真生效（重新讀取、fetch URL、查 DB）
- **批量腳本**：不裸跑整批；先小筆驗證、再逐筆或精準參數執行
- **規則一句話**：宣稱「完成／通過」前，先想「我看到了什麼可驗證的證據」；拿不到證據就說「待驗證」，不算完成
